# IEC 62304 — Medical Device Software Life Cycle Processes

## TL;DR
IEC 62304 is the international standard for medical device software life cycle processes. It defines the activities a manufacturer must perform from development planning through post-market maintenance, and ties the depth of those activities to the software's safety class (A, B, or C). It is recognized by the US FDA, Health Canada, the TGA (Australia), and is being harmonized under EU MDR/IVDR. Pair it with ISO 14971 (risk management) and ISO 13485 (quality management) and you have the full regulatory frame for SaMD and SiMD.

## Why it matters
If you build software that ends up in a medical device — embedded (SiMD) or standalone (SaMD) — IEC 62304 is almost certainly in scope. The standard gives FDA reviewers a structured way to assess your software development process, and not having it documented is a common reason for 510(k) and De Novo submissions to stall. The "process rigor" scales with the safety class, so low-risk software (Class A) has minimal process burden while life-supporting or life-sustaining software (Class C) has the full set of activities. The 2015 amendment added clarifications on risk management, software system testing, and configuration management that the original 2006 edition left ambiguous.

## Key ideas
- **Software safety classification** — A (no injury possible), B (non-serious injury), C (death or serious injury). The classification drives the depth of required activities: a Class A system can have a single developer, a Class C system needs full requirements traceability, detailed design, unit testing, integration testing, and system testing.
- **Five main processes** — (1) software development planning, (2) software requirements analysis, (3) software architectural and detailed design, (4) software unit implementation and verification, (5) software integration and system testing. Plus four supporting processes: maintenance, risk management, configuration management, problem resolution.
- **Requirements traceability is mandatory** — every software requirement must trace to a system requirement and to a risk control measure (per ISO 14971). This is the single most common audit finding: missing or broken traceability.
- **Software risk management is integrated with ISO 14971** — software contributing to a hazardous situation must be identified, the risk evaluated, and risk control measures implemented in software. Each control must be verified in software.
- **Legacy software is allowed** — if the manufacturer can justify that pre-existing software was developed under a comparable process, it can be used without full re-development. The justification and the evidence become part of the technical file.
- **Maintenance is a regulated lifecycle phase** — every change to released software must be evaluated for impact on safety, re-tested, and documented. Bug fixes, security patches, and feature updates are all in scope.
- **The 2015 amendment clarified** — configuration management scope, software problem resolution, and the relationship between the software development plan and the quality system. Edition 2 (in development) is expected to add explicit cybersecurity and agile development guidance.

## So what
Map your existing software development process to IEC 62304's five main processes and assess the gaps by safety class. Most organizations find that the planning and risk management processes need the most work — these are the sections that FDA reviewers examine first. Use a traceability matrix tool (many off-the-shelf ALM tools support this) from day one; retroactively tracing requirements is much more painful. If you're building SaMD, also look at IEC 82304-1 (health software — general requirements for product safety) which sits above IEC 62304 for standalone software.

## When to use
- You develop or maintain software for a medical device (SiMD or SaMD)
- You're preparing a 510(k), De Novo, or CE marking submission
- You're an FDA, Health Canada, or TGA reviewer looking for the standard of practice
- You're integrating IEC 62304 with an agile or DevOps toolchain (the standard is methodology-agnostic but the documentation expectations are not)
- You need to defend a software change as "no impact to safety" during post-market maintenance
